## Summary

SINARCA today has zero PostGIS/geometry usage anywhere in the schema. The "geofence" that exists is not stored — it is recomputed on every render from `project_tags` (4+ lat/lng rows per project, one per QTAG vertex) using an identical polar-angle-sort + shoelace-formula algorithm duplicated in Python (`backend_app/modules/projects/service.py::_polygon_area`) and TypeScript (`src/services/projectOrigination.ts::orderTagsForPolygon` + `calculatePolygonArea`). Both implementations agree exactly (same centroid-based `atan2` sort, same shoelace sum). Crucially, the backend's `_polygon_area` is used **only for a >0 validation check** — the actual polygon shown to users on `/projeto/:id` and in the certifier review is built **client-side**, because `ProjectGeofencePreview.tsx` receives raw `tags` (converted to `ProjectTagDraft[]`) and always recomputes ordering/area itself, regardless of whether the tags came from a draft form or from a persisted project.

This phase's job is narrow and mechanical: introduce PostGIS, add one new table (`project_boundaries`) with 4 `geometry(Polygon, 4326)` columns keyed to `projects`, backfill `declared_boundary` for every project that already has `project_tags`, add server-side geometry validation using PostGIS functions before any future write, add an overlap-detection query, and change exactly the three call sites that render `ProjectGeofencePreview` from persisted data (`MrcaDetails.tsx`, `CertifierReview.tsx`) to pass the stored geometry instead of re-deriving it — while leaving `AddProject.tsx`'s live wizard preview (which has no persisted project yet) on the existing client-side draft computation.

Supabase's Postgres distribution ships PostGIS pre-installed as one of its 50+ bundled extensions (both locally via the CLI Docker image and in hosted projects) — enabling it is a one-line `CREATE EXTENSION IF NOT EXISTS postgis;` in a new migration, no image changes needed. The project has no GeoAlchemy2 or Shapely dependency; the codebase's existing pattern is 100% SQLAlchemy 2.0 async ORM with typed models, and zero use of raw `text()` SQL anywhere in `backend_app/`. This phase will be the first to introduce raw parameterized SQL (via `sqlalchemy.text()`) for geometry construction/validation/query, since GeoAlchemy2 is unnecessary added complexity for a use case that only needs a handful of PostGIS function calls (`ST_MakePolygon`, `ST_GeomFromText`, `ST_IsValid`, `ST_Area`, `ST_Intersects`) rather than full ORM geometry mapping.

**Primary recommendation:** Add PostGIS via a plain `create extension` migration; create `project_boundaries` as a new table (never touch `project_tags`) with a `geometry(Polygon, 4326)` column per boundary type, a FK + unique index on `project_id`, and a GiST index on `active_boundary` (the column actually queried for overlap); build the polygon server-side in Python by re-running the *exact same* centroid + `atan2` ordering algorithm already used at runtime (do not invent a new ordering), close the ring, and hand the WKT to `ST_GeomFromText($1, 4326)` via a bound parameter (never string-interpolate coordinates into SQL); validate with `ST_IsValid`/`ST_IsSimple`/vertex-count/duplicate-vertex checks before insert; backfill by running that same construction against the current (already-migration-repaired) `project_tags` rows in a single idempotent `INSERT ... ON CONFLICT (project_id) DO UPDATE` migration that runs after `202605260002_repair_legacy_qtag_geofences.sql` in migration order; and change only `MrcaDetails.tsx` / `CertifierReview.tsx` to source `ProjectGeofencePreview` from a new `boundary` (GeoJSON) field added to `ProjectPublicDossierResponse.tags`-sibling payload, not from `dossier.tags`.

### Pattern 1: Server-side polygon construction reusing the existing ordering algorithm

**What:** Before inserting into `project_boundaries`, order the vertex list using the *same* centroid + `atan2` polar-angle sort already implemented in `_polygon_area()` (backend) and `orderTagsForPolygon()` (frontend), then close the ring (repeat the first point) and build WKT.

**When to use:** Every time `project.tags` are created or replaced (`create_project`, `update_project`), immediately after the existing `validate_project_tags()` call and tag persistence loop.

**Why reuse, not reinvent:** The user constraint explicitly requires "sem perda de área/vértices em relação ao cálculo shoelace anterior" (GEOF-02). Any new ordering algorithm (e.g., PostGIS's own convex-hull-based ordering) could silently produce a different polygon for non-convex QTAG layouts. Reusing the identical Python ordering guarantees the persisted geometry matches what users have seen since Phase 3.

**Example:**
```python
# backend_app/modules/projects/service.py (new function, near _polygon_area)
# Source: existing _polygon_area (this repo, verified) — same centroid+atan2 ordering,
# adapted to return the ordered ring instead of just the area.

def _ordered_ring(coordinates: list[tuple[float, float]]) -> list[tuple[float, float]]:
    """Same ordering as _polygon_area(): centroid + atan2 polar-angle sort.
    Returns points as (lat, lng) tuples in polygon order, NOT yet closed."""
    center_lat = sum(lat for lat, _ in coordinates) / len(coordinates)
    center_lng = sum(lng for _, lng in coordinates) / len(coordinates)
    return sorted(coordinates, key=lambda item: math.atan2(item[0] - center_lat, item[1] - center_lng))


def _polygon_wkt(coordinates: list[tuple[float, float]]) -> str:
    """Builds WKT POLYGON from (lat, lng) tuples.
    IMPORTANT: WKT/PostGIS coordinate order is (X Y) = (longitude latitude) —
    the OPPOSITE of this codebase's (latitude, longitude) tuple convention.
    Ring must be explicitly closed (first point repeated at the end)."""
    ring = _ordered_ring(coordinates)
    closed = ring + [ring[0]]
    points = ", ".join(f"{lng} {lat}" for lat, lng in closed)  # note: lng first
    return f"POLYGON(({points}))"
```

### Pattern 2: Server-side geometry validation before persist (GEOF-03)

**What:** A dedicated validation step that runs PostGIS checks (`ST_IsValid`, `ST_IsSimple` for self-intersection) plus Python-side checks (minimum vertex count, duplicate vertices, closed ring) plus an area-divergence check (declared vs. calculated), mirroring Bible §14 and §7 exactly.

**When to use:** Immediately before the INSERT/UPDATE into `project_boundaries`, in the same transaction as tag persistence, so a bad polygon never reaches the database.

**Example:**
```python
# Python-side checks (cheap, no DB round trip) — do first:
def _validate_ring_shape(coordinates: list[tuple[float, float]]) -> None:
    if len(coordinates) < 4:
        raise HTTPException(400, "Polígono precisa de no mínimo 4 vértices")
    if len(set(coordinates)) != len(coordinates):
        raise HTTPException(400, "Vértices duplicados não são permitidos")
    if any(lat < -90 or lat > 90 or lng < -180 or lng > 180 for lat, lng in coordinates):
        raise HTTPException(400, "Coordenadas fora do intervalo válido")

# PostGIS-side checks (one round trip, authoritative for topology):
result = (await self.session.execute(
    text(
        """
        select
          ST_IsValid(g) as is_valid,
          ST_IsValidReason(g) as invalid_reason,
          ST_IsSimple(g) as is_simple,          -- false => self-intersection
          ST_Area(g::geography) / 10000.0 as calculated_area_ha
        from (select ST_GeomFromText(:wkt, 4326) as g) t
        """
    ),
    {"wkt": wkt},
)).mappings().one()

if not result["is_valid"]:
    raise HTTPException(400, f"Geometria inválida: {result['invalid_reason']}")
if not result["is_simple"]:
    raise HTTPException(400, "Polígono possui autointerseção")

declared_area_ha = float(project.area_hectares)
calculated_area_ha = float(result["calculated_area_ha"])
divergence_pct = abs(declared_area_ha - calculated_area_ha) / max(declared_area_ha, 1e-9) * 100
# Threshold not specified by Bible — flag as Open Question for planner/user to set
# (Bible §7 example shows 0.32% ACCEPTED, no example of a REJECTED numeric threshold).
```

**Note on `ST_Area` and hectares:** `ST_Area(geometry)` on a `geometry(Polygon, 4326)` column returns an area in *square degrees*, which is meaningless for hectares. Cast to `geography` first (`ST_Area(g::geography)`) to get an area in square meters (geography type uses a spherical/geodesic calculation), then divide by 10,000 for hectares. This is a common PostGIS pitfall — see Common Pitfalls.

### Pattern 3: Idempotent backfill migration (GEOF-02)

**What:** A SQL migration that computes `declared_boundary` for every project that has ≥4 `project_tags` rows and no existing `project_boundaries` row, using SQL-native equivalents of the centroid+atan2+shoelace algorithm, then upserts so re-running the migration never duplicates or corrupts data.

**Precedent in this repo:** `202605260002_repair_legacy_qtag_geofences.sql` already establishes the pattern of a defensive, idempotent, targeted `UPDATE ... FROM (cte) WHERE` migration operating on `project_tags`. This backfill migration should follow the same idiom (CTE + upsert), scoped to `project_boundaries` instead.

**Migration ordering constraint:** This backfill migration MUST be numbered/timestamped to run *after* `202605260002_repair_legacy_qtag_geofences.sql` (which it already will be, since any new migration in this phase is dated 2026-08-15 or later). This guarantees the backfill reads the *already-repaired* coordinates for the seed project that had collinear placeholder QTAGs — see `## Open Questions` for the resolved reasoning.

**Example (SQL-native ordering, avoids a round trip to Python for every project):**
```sql
-- supabase/migrations/2026081500XX_backfill_declared_boundaries.sql
-- Idempotent: re-running never duplicates rows (upsert on project_id) and
-- always re-derives from the CURRENT project_tags state, so it is safe to
-- re-run after further tag edits too.

with tag_points as (
  select
    t.project_id,
    t.latitude,
    t.longitude,
    p.latitude as center_lat_seed,   -- not used for ordering; centroid computed below
    p.id as project_pk
  from project_tags t
  join projects p on p.id = t.project_id
),
centroids as (
  select project_id, avg(latitude) as c_lat, avg(longitude) as c_lng, count(*) as vertex_count
  from tag_points
  group by project_id
  having count(*) >= 4
),
ordered as (
  select
    tp.project_id,
    tp.latitude,
    tp.longitude,
    -- same centroid + atan2 polar-angle ordering as the Python/TS implementations
    atan2(tp.latitude - c.c_lat, tp.longitude - c.c_lng) as angle
  from tag_points tp
  join centroids c on c.project_id = tp.project_id
),
rings as (
  select
    project_id,
    -- ST_MakePoint(x, y) = ST_MakePoint(longitude, latitude) — PostGIS is (X,Y) = (lng, lat)
    ST_MakeLine(array_agg(ST_SetSRID(ST_MakePoint(longitude::float8, latitude::float8), 4326) order by angle))
      as open_line
  from ordered
  group by project_id
),
polygons as (
  select
    project_id,
    -- close the ring: ST_MakePolygon requires a closed LineString
    ST_MakePolygon(ST_AddPoint(open_line, ST_StartPoint(open_line))) as boundary
  from rings
)
insert into project_boundaries (project_id, declared_boundary, declared_area_ha, declared_source, created_at)
select
  project_id,
  boundary,
  round((ST_Area(boundary::geography) / 10000.0)::numeric, 4),
  'backfill_qtag_shoelace_v1',
  now()
from polygons
where ST_IsValid(boundary)  -- defensive: never insert an invalid backfilled polygon
on conflict (project_id) do update set
  declared_boundary = excluded.declared_boundary,
  declared_area_ha = excluded.declared_area_ha,
  declared_source = excluded.declared_source;
```

This SQL-native version is offered as the primary backfill approach (single migration, no app-code dependency, matches the repair migration's SQL-only idiom). An equivalent Python/asyncpg script is also viable if the planner prefers running backfill logic through the same `_polygon_wkt()` helper used at request time for absolute algorithm parity — but that requires a one-off script or a startup hook, which is more moving parts than a plain SQL migration for this dataset's size (7 seed projects, 1 with tags today).

### Pattern 4: Overlap detection (GEOF-04)

**What:** A query comparing one project's `active_boundary` against every *other* project's `active_boundary`, using `ST_Intersects` as a cheap pre-filter (uses the GiST index) and `ST_Area`/`ST_Intersection` only for projects that actually intersect.

**Where it should live:** A new method on `ProjectsService` (e.g. `detect_boundary_overlaps(project_id) -> list[OverlapResult]`), NOT a database trigger. Rationale:
- The Bible (`14_Novos_requisitos.md` §17) explicitly states overlap does not automatically mean fraud — it requires the Conflict/Risk Engine (Phase 04.2) to interpret it. A DB trigger that fires on every write would force interpretation logic into SQL, which belongs in Phase 04.2's service layer, not this phase's schema layer.
- This phase's acceptance criteria only requires "detecção interna" and `overlapPercentage` calculation — it does not require automatic conflict record creation (that's `INTG-03` in Phase 04.2). Keeping this as a callable service method (invoked on project create/update, and optionally exposed as an endpoint) keeps this phase's surface area correctly scoped and leaves Phase 04.2 free to decide *when* to call it (sync on write vs. async job).

**Example:**
```sql
-- Overlap detection: cheap ST_Intersects pre-filter (uses GiST index),
-- then ST_Area(geography) for the percentage only on actual intersections.
select
  other.project_id as related_project_id,
  ST_Area(ST_Intersection(mine.active_boundary, other.active_boundary)::geography) / 10000.0
    as overlap_area_ha,
  (
    ST_Area(ST_Intersection(mine.active_boundary, other.active_boundary)::geography)
    / nullif(ST_Area(mine.active_boundary::geography), 0)
  ) * 100 as overlap_percentage
from project_boundaries mine
join project_boundaries other
  on other.project_id != mine.project_id
  and ST_Intersects(mine.active_boundary, other.active_boundary)   -- GiST-indexed, cheap
where mine.project_id = :project_id;
```

Note: `active_boundary` is what Bible §8 recommends as the "geometry currently considered by the system" (priority `CERTIFIED > FIELD_VERIFIED > DECLARED`). Since this phase only populates `declared_boundary` via backfill, `active_boundary` must also be populated (at minimum, mirrored from `declared_boundary`) at write time, or overlap detection has nothing to query — see Open Questions.

### Anti-Patterns to Avoid

- **String-interpolating lat/lng floats directly into SQL text (`f"POLYGON(({lat} {lng}, ...))"` passed straight to `session.execute(text(sql_with_values_baked_in))`):** Even though coordinates are numeric (not free text), building the *entire* SQL statement via f-string with values inlined is a SQL injection anti-pattern and bypasses SQLAlchemy's parameter binding/type coercion. Always pass the WKT string itself as a *bound parameter* (`:wkt`) to `ST_GeomFromText(:wkt, 4326)`, never bake coordinate values into the SQL string that gets sent to `session.execute()` as the query text.
- **Swapping lat/lng order:** This codebase stores/consumes `(latitude, longitude)` everywhere (Postgres `project_tags` columns, Python tuples, Leaflet `[lat, lng]`). PostGIS/WKT/GeoJSON use `(longitude, latitude)` = `(X, Y)`. Every geometry-construction site must explicitly reverse the order — get this wrong and polygons will be mirrored/rotated in ways that pass basic validity checks but are geographically wrong.
- **Using `ST_Area(geometry)` directly for hectares:** Returns square *degrees* on a `geometry(Polygon, 4326)` column, not square meters. Always cast to `geography` first: `ST_Area(g::geography)`.
- **Re-deriving polygon ordering with a different algorithm than the one already in production:** Would violate GEOF-02's "no loss of area/vertices vs. previous shoelace calc" acceptance rule. Reuse the existing centroid+atan2 ordering exactly (both in the backfill migration and in any new backend service code).
- **Treating `project_tags` as replaceable by `project_boundaries`:** CONTEXT.md is explicit that `project_tags` stays as-is (physical QTAG/NFC identity). `project_boundaries` is additive, not a replacement.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Polygon self-intersection detection | A custom Python line-segment-intersection checker | PostGIS `ST_IsSimple()` | PostGIS's implementation is battle-tested against edge cases (near-collinear points, floating point precision at the poles/antimeridian) that a hand-rolled checker would get wrong |
| Polygon validity (ring closure, minimum ring size, self-touching) | Custom Python validators | PostGIS `ST_IsValid()` + `ST_IsValidReason()` | `ST_IsValidReason()` also gives a human-readable diagnostic string for free, useful for the 400 error detail |
| Geodesic area calculation (hectares from lat/lng polygon) | Haversine-based custom area formula in Python | PostGIS `ST_Area(geometry::geography)` | The existing `_polygon_area`/`calculatePolygonArea` shoelace formula treats lat/lng as flat Cartesian coordinates, which is a **known approximation** that only survives at small scales; `ST_Area(::geography)` performs a proper geodesic calculation. This is itself a strong argument for making PostGIS the *authoritative* area source going forward (backend `_area_from_tags`, which is used for `projects.area_hectares` today, is a separate, even cruder heuristic — out of scope to fix in this phase, but worth flagging for the planner) |
| Overlap/intersection area calculation | Custom polygon-clipping code | PostGIS `ST_Intersection()` + `ST_Area(::geography)` | Polygon clipping is a classical hard geometry problem (Sutherland-Hodgman, Weiler-Atherton, etc.) with many edge cases; PostGIS's GEOS-backed implementation handles all of them |
| Spatial "does A overlap B" pre-filtering across many projects | A Python loop computing intersects for every project pair | PostGIS `ST_Intersects()` with a GiST index on the geometry column | `ST_Intersects` on a GiST-indexed column uses the index's bounding-box pre-filter automatically, turning an O(n) full scan with per-pair geometry math into an indexed lookup — this only works if the GiST index exists (see schema requirements) |

**Key insight:** Every one of this phase's validation/overlap requirements maps 1:1 to a well-known PostGIS function. There is no part of GEOF-01..05 that requires custom geometry algorithms in application code beyond re-using the *existing* vertex-ordering logic (which must be reused, not reinvented, per GEOF-02).

## Common Pitfalls

### Pitfall 1: Coordinate order swap (lat/lng vs lng/lat)

**What goes wrong:** A polygon gets built with `POINT(lat lng)` instead of `POINT(lng lat)`, producing a geometry that is topologically valid (passes `ST_IsValid`) but geographically wrong — e.g. a project in Tocantins (lat ≈ -10, lng ≈ -48) ends up plotted somewhere in the South Atlantic or gets rejected by SRID 4326's implicit lat ∈ [-90,90]/lng ∈ [-180,180] bounds only by coincidence.

**Why it happens:** Every other part of this codebase (Python tuples, `project_tags` columns, Leaflet API, this repo's own `(latitude, longitude)` naming convention) uses lat-first ordering. PostGIS/WKT/GeoJSON is lng-first (X, Y). It is very easy to copy-paste a `(lat, lng)` tuple into a WKT builder without swapping.

**How to avoid:** Centralize WKT/GeoJSON construction in exactly one helper function (`_polygon_wkt` in the pattern above) with an explicit inline comment on the swap, and never build WKT ad hoc elsewhere.

**Warning signs:** A backfilled/created polygon's centroid, when reversed, matches a real place; or `ST_IsValid` passes but the rendered map preview shows the polygon in the wrong hemisphere/region.

### Pitfall 2: `ST_Area` without `::geography` cast silently returns nonsense for hectares

**What goes wrong:** `ST_Area(declared_boundary)` on a `geometry(Polygon, 4326)` column returns a number in square *degrees of latitude/longitude*, not square meters. Dividing that by 10,000 does not give hectares — it gives a meaningless tiny or huge number depending on latitude.

**Why it happens:** `ST_Area` has an overload for both `geometry` and `geography` types; PostGIS will happily accept a `geometry(..., 4326)` input to the `geometry` overload without erroring, since SRID 4326 is technically a valid (if degenerate for area purposes) planar CRS as far as the function signature is concerned.

**How to avoid:** Always write `ST_Area(column::geography)` for any area calculation intended for real-world units (hectares, m²). This repo's own area-divergence check (GEOF-03) and overlap percentage (GEOF-04) both depend on this being correct.

**Warning signs:** Area-divergence validation rejects every single project even for a manually verified accurate polygon, or accepts wildly wrong polygons — either symptom indicates the geography cast is missing.

### Pitfall 3: Migration ordering and the repair migration's already-fixed data

**What goes wrong:** If the backfill migration re-derives geometry from *original, unrepaired* collinear placeholder coordinates (e.g. by trying to detect and special-case the old `-10.11..-10.14 / -48.31..-48.34` pattern), it will either produce a degenerate line polygon (rejected by `ST_IsValid`/area>0 checks) or require duplicating the repair migration's fix logic.

**Why it happens:** Someone reading the CONTEXT.md open question literally ("deve re-derivar dos pontos brutos... ou ler as coordenadas já reparadas?") might think there's ambiguity requiring a design decision.

**How to avoid — resolved by this research:** There is no real ambiguity. `202605260002_repair_legacy_qtag_geofences.sql` is a `project_tags` **data** migration that runs once, at a fixed point in migration history, and permanently overwrites the `latitude`/`longitude` columns for the affected rows. Any migration numbered after it (which any new 04.1 migration necessarily is, being dated 2026-08-15+) will see the *already-repaired* coordinates when it queries `project_tags` — there is no "original" data left to re-derive from; the repair migration already mutated the table in place. **The backfill migration should simply read current `project_tags` rows as-is** (as the Pattern 3 SQL above does) — this is both the only viable approach and the correct one, since `project_tags` is the single source of truth for QTAG coordinates and always has been. No special-casing of the repair migration's output is needed or possible.
**Note for planner:** In a fresh local `npx supabase db reset`, only 1 of 7 seed projects (`PRC-2024-002`) actually has `project_tags` rows in the current `supabase/seed.sql` — the collinear placeholder data the repair migration targets does not exist in the current seed file (it may have existed in an earlier seed revision, or applies to non-seed/staging data created via the app). This means the backfill migration's *effective* scope on a fresh local reset is exactly 1 project; the migration's logic must still be written generally (any project with ≥4 tags), not hardcoded to that one project.

### Pitfall 4: Vertex count is not fixed at 4

**What goes wrong:** Code (or a plan) assumes exactly 4 vertices (A/B/C/D) per project, since that's what today's UI enforces as the *minimum* and what all current seed data has.

**Why it happens:** `MIN_PROJECT_TAGS = 4` in `projectOrigination.ts` and `validate_project_tags` both enforce a minimum of 4, and the wizard defaults to exactly 4 labeled A-D. But both frontend (`addProjectTagDraft`/`getNextVertexLabel`, supporting labels beyond D) and the Bible (`15_...md` §5: "Mínimo: 4 vértices. Máximo: sem limite lógico") explicitly support more than 4.

**How to avoid:** Any WKT/polygon-building code (backend service, backfill migration) must handle an arbitrary-length vertex list, not assume exactly 4. The SQL backfill pattern above (`array_agg(... order by angle)`) already does this correctly since it aggregates however many `project_tags` rows exist per project.

### Pitfall 5: RLS blocks direct client reads of `project_boundaries` by default — this may be intentional

**What goes wrong:** After creating `project_boundaries` with RLS enabled but no `grant select`/policy for `anon`/`authenticated` (matching the `certification_pendencies`/`treasury_authorizations` convention), any code path that tries to query it directly via the Supabase JS/PostgREST client from the frontend will get zero rows or a 401/403, even for public projects.

**Why it happens — and why it's likely correct:** This repo's established convention (confirmed in `202605220002_rls_policies.sql` and `202608150001_certification_workbench.sql`) is: public-readable operational data (projects, project_tags, certifications, audits) gets an explicit `grant select` + permissive RLS policy; sensitive/internal-only operational tables get RLS enabled with **no** select policy at all, relying exclusively on `backend_app`'s service-role/application connection (which bypasses RLS) to serve data through vetted, minimized API responses.

**Decision needed from planner:** `project_boundaries` sits between these two patterns — the *geometry itself* is arguably public information already shown in `ProjectGeofencePreview` for any project a user can already view, but exposing raw geometry columns directly via PostgREST/anon-select would bypass the backend's response minimization (e.g. the public dossier deliberately excludes internal notes on other tables per D-20/D-22 in STATE.md). **Recommendation: follow the operational-table pattern (no select policy for anon/authenticated) and serve `project_boundaries` exclusively through the existing `get_public_dossier`/certifier-review backend endpoints** (as GeoJSON via `ST_AsGeoJSON`), consistent with how `project_tags` — despite being public — is still *rendered* only through backend-served payloads in this codebase's actual frontend usage (no direct PostgREST calls to `project_tags` were found in `src/`). This avoids opening a second, redundant, harder-to-minimize read path for the same data. Confirm this is Claude's discretion vs. requiring explicit user sign-off during planning, since it's a security-relevant deviation-from-symmetry decision.

### Python: geometry helper + validation (backend_app/modules/projects/service.py)
```python
# Source: this research, combining existing _polygon_area ordering logic
# (verified in this repo) with PostGIS docs for ST_IsValid/ST_IsSimple/ST_Area.
import math
from sqlalchemy import text


def _ordered_ring(coordinates: list[tuple[float, float]]) -> list[tuple[float, float]]:
    center_lat = sum(lat for lat, _ in coordinates) / len(coordinates)
    center_lng = sum(lng for _, lng in coordinates) / len(coordinates)
    return sorted(coordinates, key=lambda item: math.atan2(item[0] - center_lat, item[1] - center_lng))


def _polygon_wkt(coordinates: list[tuple[float, float]]) -> str:
    ring = _ordered_ring(coordinates)
    closed = ring + [ring[0]]
    points = ", ".join(f"{lng} {lat}" for lat, lng in closed)  # PostGIS: X=lng, Y=lat
    return f"POLYGON(({points}))"


async def _validate_and_area_ha(session, wkt: str) -> tuple[bool, str | None, float]:
    row = (await session.execute(
        text(
            """
            select
              ST_IsValid(g) as is_valid,
              ST_IsValidReason(g) as invalid_reason,
              ST_IsSimple(g) as is_simple,
              ST_Area(g::geography) / 10000.0 as area_ha
            from (select ST_GeomFromText(:wkt, 4326) as g) t
            """
        ),
        {"wkt": wkt},
    )).mappings().one()
    valid = bool(row["is_valid"]) and bool(row["is_simple"])
    reason = None if valid else (row["invalid_reason"] or "Polígono possui autointerseção")
    return valid, reason, float(row["area_ha"])
```

## Open Questions

1. **Exact backfill strategy for seed projects with collinear QTAGs (the question CONTEXT.md flagged)**
   - What we know: The repair migration (`202605260002_repair_legacy_qtag_geofences.sql`) is a one-time, already-applied `UPDATE` that permanently rewrote `project_tags.latitude`/`longitude` for rows matching a specific old placeholder coordinate pattern. It runs before any 04.1 migration in the migration sequence (by filename/timestamp ordering). There is no "raw" unrepaired data left anywhere for a later migration to read — the repair mutated the table in place.
   - What's unclear: Nothing technically — this is resolved. The only residual ambiguity is whether the *current* `supabase/seed.sql` still contains rows matching the repair migration's target pattern (it does not, per direct grep in this research session) — meaning on a fresh local reset, the repair migration is a no-op today, and the backfill migration's only real seed-data target is `PRC-2024-002`.
   - Recommendation: Backfill migration reads `project_tags` as-is (current state), with no special-casing for the repair migration. Document this resolution directly in the migration's SQL comment (mirroring the repair migration's own comment style) so future readers don't re-open this question.

2. **What populates `active_boundary` in this phase?**
   - What we know: Bible §8 defines `active_boundary` as "the geometry currently considered by the system," with priority `CERTIFIED > FIELD_VERIFIED > DECLARED`. This phase only backfills/creates `declared_boundary` (per CONTEXT.md's explicit scope — `certified_boundary`/`field_verified_boundary` population is out of scope, deferred to Phase 05.1).
   - What's unclear: GEOF-04's overlap detection query (Pattern 4) reads `active_boundary`, but if nothing ever populates it in this phase, overlap detection has nothing to query and the GiST index sits empty.
   - Recommendation: In this phase, mirror `declared_boundary` into `active_boundary` at write time (both in the backfill migration and in `create_project`/`update_project`), since `DECLARED` is the only tier this phase populates and is therefore trivially the "currently considered" geometry by the priority rule. When Phase 05.1 later populates `certified_boundary`/`field_verified_boundary`, it should update `active_boundary` accordingly. Flag this as a planning decision to confirm, not a code risk — the priority logic itself is simple, but someone must decide whether "mirror declared into active" happens via application code (every write) or a generated/trigger column. Given this repo's convention of avoiding triggers in favor of explicit service-layer logic (no triggers found anywhere in `supabase/migrations/`), recommend application-code mirroring, consistent with the rest of the codebase.

3. **Where does overlap detection (GEOF-04) get invoked from, concretely?**
   - What we know: The Bible and CONTEXT.md require detection to happen ("Ao cadastrar propriedade ou projeto"), and `overlapPercentage` calculation, but this phase explicitly excludes Conflict record creation (Phase 04.2).
   - What's unclear: Whether GEOF-04 requires a new public/internal API endpoint (e.g. mirroring the Bible's suggested `POST /integrity/geometry/check`) for this phase, or whether it's sufficient to have a callable service method that Phase 04.2 wires up later.
   - Recommendation: Given this phase's Success Criteria only says overlap must be "detected" and percentage "calculated" — not exposed via any specific endpoint — the planner should decide whether to (a) add a minimal endpoint now for manual/QA verification (e.g. `GET /projects/:id/boundary-overlaps`, internal/admin-only), or (b) leave it as a service method exercised only by tests until Phase 04.2 needs it live. Recommend (a) for testability (see Validation Architecture below) — a thin endpoint costs little and lets Nyquist-style verification exercise GEOF-04 end-to-end via HTTP rather than only via a Python unit test reaching into the service layer.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| SQL injection via geometry WKT construction (raw `text()` SQL is new to this codebase in this phase) | Tampering | Always pass WKT/coordinate values as bound parameters to `session.execute(text(sql), {"wkt": wkt, ...})`; never f-string/format coordinate values directly into the SQL string passed to `text()` |
| Coordinate spoofing to claim a boundary over someone else's project (double-claiming a physical area) | Spoofing / Repudiation | Out of this phase's scope to *prevent* (that's Conflict/Risk Engine, Phase 04.2) — but this phase's overlap detection (GEOF-04) is the foundational signal that makes future prevention possible. Ensure `overlapPercentage` calculation itself cannot be bypassed by a malformed/degenerate polygon (validation in Pattern 2 must run before any overlap check has meaningful input) |
| Denial of service via pathological polygon input (extremely high vertex count, e.g. thousands of QTAG rows) | Denial of Service | Bible explicitly says "sem limite lógico definido pelo produto" for max vertices, but also allows a "limite técnico... para proteção da API e do banco" — recommend the planner add a sane upper bound (e.g. a few hundred vertices) as an API-level guard, since `project_tags` today has no upper limit enforced anywhere in `validate_project_tags` |

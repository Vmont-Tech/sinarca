# Phase 04.1 Plan 03: Internal Boundary Overlap Detection Summary

**`ProjectsService.detect_boundary_overlaps` uses a GiST-indexed `ST_Intersects` pre-filter plus `ST_Area(ST_Intersection(...)::geography)` to compute `overlapPercentage`, exposed via an authenticated, org-scoped `GET /projects/{id}/boundary-overlaps` endpoint; a deterministic two-project HTTP test observed 24.9996%/25.0004% overlap for a rectangle pair shifted half a span in both axes.**

## Accomplishments
- `ProjectsService.detect_boundary_overlaps(project_id)` added immediately after `persist_project_boundary`: joins `project_boundaries` to itself on `ST_Intersects(mine.active_boundary, other.active_boundary)` (uses the `project_boundaries_active_boundary_gix` GiST index from plan 04.1-01 as a cheap bounding-box pre-filter), then computes `ST_Area(ST_Intersection(...)::geography)` only for pairs that actually intersect — read-only, no writes, no `Conflict`/severity logic
- `overlapPercentage` (against the caller's own area) and `overlapPercentageOfRelated` (against the other project's area) both returned in camelCase, plus `overlapAreaHa`, `relatedProjectId`, `relatedProjectFriendlyId`, `relatedProjectName`
- `ProjectBoundaryOverlapsResponse` schema added to `schemas.py`; `GET /projects/{project_id}/boundary-overlaps` added to `routes.py`, guarded by `require_role("producer", "certifier", "admin")` + `_assert_project_edit_permission` — the identical org-scoped pattern used by `/projects/{id}/pendencies` — registered at `/api/v1/projects/{project_id}/boundary-overlaps` (confirmed via FastAPI route introspection)
- Deterministic integration test (`test_boundary_overlap_detection`): two rectangles built with a purpose-built `rectangle_tags()` helper (not the shared fixed-rectangle `tag_payload()`, which many prior test projects already overlap at 100%), shifted half a span in each axis so the intersection is geometrically exactly one quarter of each rectangle's area — **observed over a live HTTP call: `overlapPercentage=24.9996`, `overlapPercentageOfRelated=25.0004`, `overlapAreaHa=120.8857`**, matching the ~25% expectation within the asserted `24.0 < x < 26.0` tolerance band
- `test_boundary_overlap_excludes_disjoint_projects`: a project ~550 km away produces no overlap entry, and a project never appears as its own overlap
- `test_boundary_overlaps_requires_authentication`: anonymous GET returns 401/403, never 200
- `test_detect_boundary_overlaps_uses_gist_index`: asserts `project_boundaries_active_boundary_gix` exists in `pg_indexes` and its `indexdef` contains both `gist` and `active_boundary`
- Full backend suite: 132 passed, 1 pre-existing unrelated failure (same `test_frontend_container_proxies_api_requests_to_backend_service` Dockerfile assertion failure documented in both 04.1-01 and 04.1-02 SUMMARYs — out of this plan's scope)

## Decisions Made
- Overlap detection stays a callable service method + read endpoint, never a DB trigger, per the plan's explicit design decision (resolves RESEARCH.md Open Question #3) — this repo has zero triggers, and a write-time trigger would push interpretation logic (Phase 04.2's job) into SQL.
- Both overlap percentages (`overlapPercentage` against the caller's area, `overlapPercentageOfRelated` against the other project's area) are returned, since the two areas can differ.
- The endpoint requires authentication and org-scoped authorization identical to `/projects/{id}/pendencies` — anonymous access (`optional_user`) is explicitly forbidden, since overlap results disclose the existence and geometric proximity of third-party projects (T-041-11).

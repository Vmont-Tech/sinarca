# Phase 04.1 Plan 05: Render Persisted Boundary Geometry in the Frontend Summary

**`ProjectGeofencePreview` now accepts an optional `boundary` GeoJSON Polygon prop and renders server-persisted geometry (converting `[lng,lat]` to `[lat,lng]`) at the two call sites showing a persisted project, while the origination wizard keeps its live client-side recompute -- browser-verified end-to-end on the public dossier against the live API payload.**

## Accomplishments

- Added `PersistedBoundaryPolygon` (`{ type: 'Polygon'; coordinates: number[][][] }`) and `ProjectBoundaryPayload` types to `src/services/database.ts`; added `boundary: ProjectBoundaryPayload | null` to `ProjectPublicDossier`, right after `baseline`.
- `src/services/certifierReview.ts` imports `ProjectBoundaryPayload` from `./database` and adds `boundary: ProjectBoundaryPayload | null` to `CertifierReviewDossier`, right after `baseline`.
- `ProjectGeofencePreview` gained an optional `boundary?: PersistedBoundaryPolygon | null` prop (default `null`). A new `persistedPoints` memo derives Leaflet-ready `CoordinateTag[]` from `boundary.coordinates[0]`, guarding against a missing/too-short ring (`ring.length < 4` -> `[]`), dropping the GeoJSON-closed ring's duplicated last point (`slice(0, -1)`), and explicitly destructuring `[lng, lat]` into `latitude: lat, longitude: lng` (coordinate-swap guard, T-041-21).
- `usesPersistedBoundary` (`persistedPoints.length >= MIN_PROJECT_TAGS`) now gates `hasArea`, `shouldRenderMap`, `polygonPoints` and `mapPoints`, so the Leaflet map, SVG technical preview and "área válida" badge all render from server geometry when present, and transparently fall back to the pre-existing client-side `orderTagsForPolygon`/`calculatePolygonArea` computation when `boundary` is absent or null (T-041-19 malformed-ring guard).
- `orderTagsForPolygon`, `calculatePolygonArea`, `MIN_PROJECT_TAGS`, and the rest of `src/services/projectOrigination.ts` were left untouched -- confirmed by `git diff --name-only` not including that file.
- `MrcaDetails.tsx` (~line 302): `<ProjectGeofencePreview tags={qtagDrafts} boundary={dossier.boundary?.declared ?? null} />`, with an explanatory code comment.
- `CertifierReview.tsx` (~line 484, "QTAGs / Geofence" tab): `<ProjectGeofencePreview tags={qtagDrafts} boundary={review.boundary?.declared ?? null} />`. Confirmed `review` is non-null at that JSX position (guarded by the enclosing `{review && (...)}` block at ~line 382), so no optional-chaining-on-possibly-undefined risk beyond the already-optional `.boundary`.
- `AddProject.tsx`'s two wizard call sites (`~1596`, `~1741`) were left as `<ProjectGeofencePreview tags={tags} />` with no `boundary` prop, each preceded by an explicit rationale comment (`GEOF-05: intencionalmente SEM a prop boundary...`), per the plan's locked call-site disposition table. `applyProjectForEditing`/`editingProjectId` flow untouched.
- `npm run build` passes after each task (vite build, no TypeScript errors surfaced by the build step; `npx tsc -b` intentionally not used per plan and STATE.md's documented pre-existing legacy-debt block).
- All grep-level structural acceptance criteria from both tasks passed verbatim (call-site counts, coordinate-swap guard, `usesPersistedBoundary` reference count >= 5, fallback path preserved, wizard rationale comment count == 2, no `ProjectGeofencePreview` line was deleted in `AddProject.tsx`).

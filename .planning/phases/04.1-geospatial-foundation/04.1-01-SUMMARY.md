## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Backfill migration produced 0 rows on a fresh `npx supabase db reset`**
- **Found during:** Task 3 (live database verification)
- **Issue:** `npx supabase db reset` applies every file in `supabase/migrations/` (in order) BEFORE running `supabase/seed.sql`. The backfill migration (`202608150004_backfill_declared_boundaries.sql`) therefore ran against an empty `project_tags` table on every fresh local reset, since `project_tags` rows for `PRC-2024-002` are only inserted later, by `seed.sql`. The plan's own must-have truth ("The seed project PRC-2024-002 has a `declared_boundary` row after `npx supabase db reset`") failed on first verification: `select count(*) from project_boundaries` returned `0`.
- **Fix:** Appended the exact same idempotent backfill SQL body (the identical CTE + `insert ... on conflict (project_id) do update`) to `supabase/seed.sql`, immediately after the `project_tags` insert statement. Since the logic is byte-for-byte the same idempotent upsert as the migration, re-running it a second time (e.g. if a non-local environment already backfilled real data via the migration) is safe and produces no duplicate.
- **Files modified:** `supabase/seed.sql`
- **Verification:** Re-ran `npx supabase db reset`; `project_boundaries` now has 1 row for `PRC-2024-002` with `declared_vertex_count=4`, `ST_NPoints=5`, `ST_IsValid=true`, `active_boundary_tier='DECLARED'`, `ST_Equals(declared_boundary, active_boundary)=true`.
- **Committed in:** `8d100db` (Task 3 commit)

**2. [Rule 1 - Bug] `test_backfill_is_idempotent` failed under the full test suite due to a too-broad assertion**
- **Found during:** Task 3, running `uv run pytest -q` (full backend suite)
- **Issue:** The test originally asserted the *global* `project_boundaries` row count was unchanged before/after re-running the backfill migration's SQL. Under the full suite, other tests (e.g. `tests/test_api_integration.py`) create additional projects with `project_tags` via the API — those projects are not yet backfilled at write time (that's out of scope for this plan, deferred to a later 04.1 plan that wires backfill into `create_project`/`update_project`). Re-running the migration SQL legitimately inserts new `project_boundaries` rows for those other projects, so the global count grew from 1 to 35, failing the assertion even though nothing was duplicated for `PRC-2024-002`.
- **Fix:** Scoped the idempotency assertion to `PRC-2024-002` specifically (join `project_boundaries` to `projects` filtered by `friendly_id`), asserting the count for that one project stays at exactly 1 before and after re-running the migration — which is what "does not create a duplicate project_boundaries row" (the plan's actual must-have) means.
- **Files modified:** `tests/test_project_boundaries.py`
- **Verification:** `uv run pytest -q` — 120 passed, 1 pre-existing unrelated failure (see Issues Encountered).
- **Committed in:** `8d100db` (Task 3 commit)

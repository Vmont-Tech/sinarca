# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none (hand-rolled Tailwind CSS components; no Radix/Base UI/shadcn primitives anywhere in this codebase) |
| Icon library | lucide-react (`^0.562.0`, already installed — verified in `package.json`) |
| Font | `Open Sans` (`font-sans`, body default) / `Montserrat` (`font-display`, headings when explicitly applied) — from `tailwind.config.js`. Certifier/Auditor pages do not currently set an explicit `font-display` class on headings; keep that convention (rely on the global body font for `h1`/`h2` weight via `font-black`, not a separate typeface) |

**shadcn gate rationale (no question asked):** No `components.json` exists anywhere in this repo and none of the 13 planned phases have introduced one across Phases 1–3. `04-RESEARCH.md` explicitly scopes Phase 4 as "100% internal extension of existing patterns" and instructs reusing `CertifierReview.tsx`/`AuditorReview.tsx`'s exact styling approach "rather than introducing new UI dependencies." Introducing shadcn now would fragment the design system mid-project and contradicts upstream research. This contract formalizes the existing hand-rolled Tailwind system instead of gating on shadcn adoption. If a future phase wants to migrate to shadcn, that decision should be made deliberately at a phase boundary, not implicitly inside Phase 4.

## Spacing Scale

Declared values (must be multiples of 4) — this is the scale already in continuous use across `CertifierReview.tsx`, `AuditorReview.tsx`, and `MrcaDetails.tsx`; Phase 4 does not introduce a new scale, it continues the existing one:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`), tight inline padding |
| sm | 8px | Compact spacing between badge/chip and adjacent text (`gap-2`), `mt-2` |
| md | 16px | Default field/element spacing (`p-4`, `gap-4`, `mt-4`) |
| lg | 24px | Card internal padding (`p-6`), section gaps (`gap-6`, `space-y-6`) |
| xl | 32px | Card padding in dossier sections (`p-8`), major card-to-card spacing (`space-y-8`) |
| 2xl | 48px | Reserved for major section breaks if the workbench introduces a full-width divider; not currently needed by existing pages |
| 3xl | 64px | Reserved for page-level top/bottom spacing; not currently needed inside `DashboardLayout` content area |

Exceptions:
- Decision action buttons (Aprovar / Solicitar ajustes / Reprovar) use `px-4 py-3` (16px/12px), producing a ~44px tap target with `text-sm` + icon — matches WCAG 2.5.5 minimum touch target and must be preserved for all three decision buttons and the certificate upload dropzone trigger.
- Micro-labels inside dense tag/vertex grids (`MrcaDetails.tsx` integrity tab) use `text-[10px]`/`text-[11px]` with `p-5` (20px) card padding — an established non-4px-multiple-adjacent exception limited to eyebrow/meta text only, never to layout spacing.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 12px (`text-xs`, uppercase, `tracking-widest`) | 700 bold | 1.2 |
| Heading | 20px (`text-xl`) | 700 bold | 1.2 |
| Display | 30px (`text-3xl`) | 700 bold | 1.2 |

Declared weights: **400 (regular, body copy)** and **700 (bold, labels/headings/buttons/emphasis)** — exactly 2, per contract.

Documented pre-existing exception (not a new weight introduced by this phase): `font-black` (900) is already used codebase-wide, without exception, for the page title (`h1`, Display role) and card/project title (`h2`, Heading role) in `CertifierReview.tsx:59/83`, `AuditorReview.tsx:353/409`, and `MrcaDetails.tsx:191/237`. Phase 4 must continue this exact convention for the workbench page title and each queue card's project title — do not downgrade existing headings to 700 to satisfy the 2-weight rule; the rule constrains *new* weight choices, not established headings. All *new* Phase 4 UI (tab labels, decision form labels, status badges, pendency copy, treasury package summary) must stick to 400/700 only — reserve 900 exclusively for the two pre-existing heading levels above.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` (white, Tailwind `bg-white`) | Page background inside `DashboardLayout`, queue card surfaces (`bg-white` cards), tab panel backgrounds |
| Secondary (30%) | `#F9FAFB` / `#F3F4F6` (Tailwind `gray-50` / `gray-100`) | Nested info panels (`bg-gray-50`), card borders (`border-gray-100`), dossier data tiles, sidebar |
| Accent (10%) | `#059669` (Tailwind `emerald-600`, chips at `emerald-50`/`emerald-700`) | See "Accent reserved for" below |
| Destructive | `#DC2626` (Tailwind `red-600`, chips at `red-50`/`red-700`) | Reprovação action, reprovação status chip, upload/atomicity error banners, remove-file/remove-pendency icon buttons |

Accent reserved for (explicit list — never "all interactive elements"):
- The **"Aprovar certificação"** primary decision button (`bg-emerald-600 hover:bg-emerald-700`)
- Dossiê-completo positive indicators (green checkmarks/`CheckCircle2` next to baseline/QTAGs/documentos once each requirement is satisfied)
- The certifier module header badge icon (`ShieldCheck`, `bg-emerald-50 text-emerald-700`, unchanged from current `CertifierReview.tsx:64`)
- The three approval status-progression labels on the card/history — "Certificação aprovada", "Mint autorizado", "Aguardando tesouraria" — rendered as completed-step chips once reached

**Additional tertiary semantic color (documented deviation from strict 60/30/10+destructive, required by the 3-way decision model already established in this codebase):**

| Role | Value | Usage |
|------|-------|-------|
| Pending/Warning | `#F59E0B` (Tailwind `amber-500`, chips at `amber-50`/`amber-700`) | The **"Solicitar ajustes"** action button; the "Aguardando retorno do produtor" queue tab label and its dashboard counter badge; open `certification_pendencies` status chips |

This third color is not a stylistic addition — it continues the exact amber-for-adjustments convention already shipped in `CertifierReview.tsx:101` and `AuditorReview.tsx:614` (`RotateCcw` "Ajustes"/"Recalcular" buttons). A binary constructive/destructive palette cannot represent a three-outcome decision (Aprovar / Solicitar ajustes / Reprovar); amber is scoped exclusively to the "needs correction, not yet a final decision" state and must never be reused for anything else (e.g., do not use amber for generic loading/info states).

## Copywriting Contract

| Secondary CTA | **"Solicitar ajustes"** (requires categoria + descrição before enabling) |
| Tertiary CTA | **"Reprovar projeto"** (requires categoria + descrição before enabling) — renamed from the legacy "Rejeitar" label in `CertifierReview.tsx:104` to match CONTEXT.md's "reprovação" terminology (D-08); apply consistently to button label, status chip, and history event copy |

(heading copy unchanged from `CertifierReview.tsx:73`; body is new — add it, don't leave the empty state as a single bare sentence) |
| Empty state — fila de ajustes | Heading: **"Nenhum projeto aguardando retorno do produtor."** Body: "Pendências enviadas para o produtor aparecem aqui até serem respondidas ou corrigidas." |
| Error state — dossiê incompleto | **"Dossiê incompleto: reúna baseline, as quatro QTAGs/geofence válidas e os documentos obrigatórios antes de decidir. Uma pendência será gerada para o produtor corrigir."** (server-enforced per D-03/D-04 — this copy must appear inline in the Decisão tab, not only as a toast) |
| Error state — falha no upload do certificado | **"Não foi possível anexar o certificado. A aprovação não foi concluída — verifique o arquivo PDF e tente novamente."** (D-14: decision stays draft/pending) |
| Error state — falha na autorização de tesouraria | **"Não foi possível registrar a autorização para a tesouraria. A aprovação foi revertida — tente novamente."** (D-19: atomic rollback, both writes fail together) |
| Destructive confirmation — Reprovar | **"Reprovar projeto"**: "Esta decisão fica registrada permanentemente no histórico e não pode ser editada. Selecione uma categoria e descreva o motivo antes de confirmar." |
| Destructive confirmation — Solicitar ajustes | **"Solicitar ajustes"**: "O projeto sai da fila principal e só retorna quando o produtor responder a esta pendência. Descreva claramente o que precisa ser corrigido." |

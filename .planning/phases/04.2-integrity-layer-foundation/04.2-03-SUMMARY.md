# Phase 04.2 Plan 03: Conflict (Geospatial Overlap Interpretation) Summary

**`IntegrityService.detect_and_persist_conflicts` turns Phase 04.1's raw ST_Intersects overlap into severity-classified, bidirectional `Conflict` rows (CLEAR->CRITICAL) with idempotent re-derivation on every geometry write, `DOUBLE_CLAIM` restricted to already-overlapping same-methodology/same-vintage pairs, and a new org-scoped `GET /projects/{id}/conflicts` — proven against real PostGIS with 9 integration tests.**

## Performance

- **Duration:** ~25 min
- **Tasks:** 3
- **Files modified:** 5 (1 created, 4 modified)

## Accomplishments

- `overlap_severity(percentage, settings=None)`: module-level pure function (testable without a session), mapping overlap percentage to `CLEAR/INFO/LOW/MEDIUM/HIGH/CRITICAL` using the configurable `integrity_overlap_severity_*_pct` thresholds from Plan 01.
- `IntegrityService.detect_and_persist_conflicts`: reuses `ProjectsService.detect_boundary_overlaps` verbatim (zero new `ST_Intersects`), builds the desired set of `GEOSPATIAL_OVERLAP` rows in both directions (so the overlapped project also sees the conflict), evaluates `DOUBLE_CLAIM` only for pairs already in that overlap set when `methodology` and `vintage` match (D-12 — never an O(n^2) global scan), then reconciles existing rows against the desired set: stale `OPEN` rows become `RESOLVED` (never deleted), matching rows get their percentage/area/severity refreshed (`CONFLICT_SEVERITY_CHANGED` audit only fires when severity actually changed), and missing rows get created (`CONFLICT_DETECTED` audit). Returns the list of related `Project` rows affected, for Plan 04's future risk recompute.
- `IntegrityService.list_conflicts`: returns `id/type/severity/status/overlapPercentage/overlapAreaHa/relatedProjectId/relatedProjectFriendlyId/detectedAt/resolvedAt`, sorted CRITICAL-first then most-recently-detected-first.
- `GET /api/v1/projects/{id}/conflicts`: same `require_role("producer","certifier","admin")` + `_assert_project_edit_permission` org-scoped guard as `/boundary-overlaps` and `/pendencies` (T-04.2-11); optional `?status` query param validated against `CONFLICT_STATUSES` with HTTP 400 on an invalid value; read-only (no POST/PUT/PATCH/DELETE routes exist for Conflict).
- Two hook points wired without touching `detect_boundary_overlaps` or `persist_project_boundary`: `create_project` (after `create_origination_claims`) and `update_project`'s `if payload.tags is not None:` branch (after `persist_project_boundary`, D-23) — so Conflict is always re-derived synchronously in the same transaction as any geometry write.
- 9 new PostGIS integration tests in `tests/test_project_conflicts.py`: HIGH severity at 25% overlap, mirroring on the related project, CRITICAL at ~100% overlap, disjoint projects generate no Conflict, resolving a Conflict by moving geometry away (without duplicating the row — D-20), resync idempotency (same PUT twice does not change the row count), `DOUBLE_CLAIM` restricted to already-overlapping pairs, the `/boundary-overlaps` response contract staying byte-for-byte unchanged (no `severity` field leaked in), and the 401 auth guard.

## Decisions Made

- `relatedProjectFriendlyId` on `DOUBLE_CLAIM` rows is intentionally `null` (that type's `metadata_` carries `methodology`/`vintage`/`basis` per the plan's exact spec, not `related_friendly_id`); `relatedProjectId` (raw uuid) is always populated and is the reliable field for identifying the related project across all Conflict types.
- The integration test resolves a project's real database uuid via a direct `projects.friendly_id` lookup (same pattern already used in `tests/test_project_boundaries.py`) rather than trusting the HTTP response's `project.id` field, which is a pre-existing legacy contract (`source_hash or str(project.id)`) unrelated to this plan.

## Deviations from Plan

None beyond the two decisions above, which are direct consequences of following the plan's exact metadata spec and pre-existing API contracts — no architectural changes, no scope creep.

## Issues Encountered

- Initial test draft matched `DOUBLE_CLAIM` rows by `relatedProjectFriendlyId`, which is only populated for `GEOSPATIAL_OVERLAP` rows per the plan's metadata spec — fixed by matching on `relatedProjectId` instead (Rule 1, self-caught during verification, no production code change needed).
- That fix initially used the HTTP response's `project["id"]` field as the expected uuid, which turned out to be the pre-existing `source_hash or str(project.id)` legacy contract, not the raw uuid stored on `Conflict.related_project_id` — fixed by resolving the real uuid via a `projects.friendly_id` DB lookup (Rule 1, test-only fix, no production code change).

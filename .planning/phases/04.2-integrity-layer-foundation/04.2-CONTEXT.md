# Phase 04.2: integrity-layer-foundation

## Origem

Inserida em 2026-08-14 a partir da ingestão de `.planning/docs/bible/14_Novos_requisitos.md` (Sinarca Integrity Layer). O princípio central da Bible é mudar `User Input → Fact` para `User Input → Claim → Evidence → Validation → Decision`: nenhuma informação crítica enviada por uma parte interessada deve receber automaticamente status de verificada. Hoje `projects.status` é um enum de workflow operacional (não um modelo de confiança), e não existe `Claim`, `Evidence` estruturada, `Conflict` ou Risk Score em nenhuma forma no schema atual — só `documents.sha256_hash` já existe como base reaproveitável de proveniência de evidência.

Esta fase não foi discutida interativamente (`/gsd-discuss-phase`) — o escopo abaixo vem direto da análise de engenharia que originou a ingestão. Antes de planejar, considerar rodar `/gsd-discuss-phase 04.2` para fechar pontos em aberto, especialmente: quais ações do sistema hoje (originação, certificação, auditoria) viram `Claim` explícito, e como `projects.status` se relaciona com o novo agregado de confiança sem quebrar os fluxos das Phases 2-4 já concluídas/planejadas.

## Escopo

- Entidades `Claim`, `Evidence`, `Conflict` conforme `.planning/docs/bible/14_Novos_requisitos.md` seção 6.
- Estados de confiança por Claim/projeto: `DECLARED → IDENTITY_VERIFIED → EVIDENCE_PENDING → EVIDENCE_VERIFIED → UNDER_REVIEW → INDEPENDENTLY_VERIFIED → VERIFIED → ON_HOLD → SUSPENDED → REVOKED → REJECTED`.
- `Evidence` referencia hash, origem, `validationMethod` e `validationStatus`, vinculada a um `Claim` — reaproveita `documents.sha256_hash` como base, não recria hashing do zero.
- `Conflict` gerado automaticamente quando `ST_Intersects` (Phase 04.1) encontra overlap acima de limiar configurável, com severidade `CLEAR → INFO → LOW → MEDIUM → HIGH → CRITICAL` (seção 16 da Bible).
- Double Claiming Engine e Duplicate Detection internos (área + atributo/benefício + período + claim, conforme seção 19-20 da Bible).
- Risk Engine: score 0-100 com sinais explicáveis (ex.: "+30 SIGEF diverge da geometria"), classes `LOW/MODERATE/HIGH/VERY_HIGH/CRITICAL` (seções 21-23).
- Auto Hold: projetos `CRITICAL` entram automaticamente em `ON_HOLD`.
- Status público nunca usa apenas "Certified" isolado — sempre explicita o que foi verificado (seção 40).

## Fora de escopo

- Four-eyes review, Integrity Console e integração com registros externos (ONR/SIGEF/CAR) — entram na Phase 05.1.
- Evidence Ledger com ancoragem Merkle real no Soroban — o `merkle_root` atual (hash único do baseline) pode evoluir depois desta fase, mas construir a árvore de Merkle de múltiplas evidências não é obrigatório para o P0.
- Identity verification real de CPF/CNPJ contra fontes oficiais — modelar o campo/estado é parte do escopo; validar contra fonte externa depende da Phase 05.1.
- Substituir `projects.status` — este continua existindo; o agregado de Claims passa a informá-lo, não o substitui de uma vez.

## Regras de aceite

- Toda submissão relevante (propriedade, metodologia, direito de operar) gera `Claim` com `status`/`confidenceScore` próprios — nenhum dado de terceiro vira "fato" sem passar por esse modelo.
- `Conflict` não pode existir sem geometria real da Phase 04.1 — esta fase depende dela.
- Nenhum projeto `CRITICAL` fica fora de `ON_HOLD` automaticamente.
- Risk Score sempre acompanha explicação legível dos sinais que o compõem — nunca só o número.

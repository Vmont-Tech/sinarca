# Phase 04.2: integrity-layer-foundation - Research

**Researched:** 2026-08-16
**Domain:** Backend data model + business rules (Claim/Evidence/Conflict/Risk Engine) over an existing FastAPI + SQLAlchemy async + Supabase Postgres/PostGIS codebase. No new external integrations.
**Confidence:** HIGH (grounded directly in current codebase and Bible PRD; low-confidence areas flagged individually below)

## Summary

Phase 04.2 does not introduce new technology — it adds three new tables (`claims`, `evidence`, `conflicts`, plus an internal-only `risk_assessments`/`risk_signals` pair) and a thin service layer on top of code that is already fully working: `detect_boundary_overlaps` (Phase 04.1) already computes `overlapPercentage` via `ST_Intersects`/`ST_Area(...::geography)`, and `documents.sha256_hash` already deduplicates by `(project_id, document_type, sha256_hash)`. The entire phase is "interpret and persist what already exists," not "build new geospatial or hashing machinery."

The critical grounding fact for planning is that **every table added to this schema since the original `initial_schema.sql` (certification_pendencies, treasury_authorizations, project_boundaries) uses plain `text` columns with `check (... in (...))` constraints for status/type fields — not new Postgres `ENUM` types**. Real Postgres `ENUM` types (`user_role`, `project_status`, `credit_status`, `ledger_entry_type`, `chain_event_type`, `external_chain`) exist only for the six enums created in the very first migration and are mapped in `models.py` via `sqlalchemy.Enum(..., create_type=False)`. New tables never re-enter that pattern. Claim/Evidence/Conflict status/type columns should follow the newer, lighter convention (`String` in `models.py`, `text ... check (...)` in SQL), not introduce `CREATE TYPE`.

The second critical grounding fact: **`backend_app/core/config.py` (`Settings`, pydantic-settings/env-based) has never actually held a business-logic threshold before.** The one existing precedent for a configurable threshold (`BOUNDARY_AREA_DIVERGENCE_WARN_PCT`, Phase 04.1) is a plain Python module-level constant in `backend_app/modules/projects/service.py:156`, not a `Settings` field. CONTEXT.md's D-10/D-13 cite `maxCloudCoverage` as the existing "config.py pattern" precedent, but `maxCloudCoverage` does not exist anywhere in the codebase yet — it is only mentioned in `REQUIREMENTS.md`/`ROADMAP.md`/Phase 05 CONTEXT.md as a still-unbuilt Phase 5 requirement. This does not block the locked decision (D-10/D-13 explicitly say `core/config.py`), but the planner should treat this as the **first real precedent** for settings-based thresholds in this codebase, not a well-trodden path — and should add fields to the existing `Settings` class rather than inventing a second config mechanism.

**Primary recommendation:** Add three new SQLAlchemy models (`Claim`, `Evidence`, `Conflict`) plus a `ProjectRiskAssessment`/`RiskSignal` pair, all following the `text + check constraint` convention (not new PG enums), hook Claim creation into `create_project` (service.py:843-893, right after `persist_project_boundary`), hook Evidence creation into the three existing `Document`-creation call sites (`submit_project_draft` service.py:737, `upload_project_document` routes.py:530, and optionally the certifier's `_persist_certificate`), extend `detect_boundary_overlaps` with a severity-computing sibling method that persists `Conflict` rows synchronously right after `persist_project_boundary`, and add a synchronous `recalculate_risk_score(project)` called after any Claim/Evidence/Conflict write — mirroring the certifier's "recalculate on the event" pattern already used for credit locking (`_ensure_locked_credit`).

### Pattern 1: Text + check-constraint enums (not Postgres ENUM types)
**What:** New status/type columns use `text not null default '...' check (col in ('A', 'B', ...))`, matching `certification_pendencies.status`, `treasury_authorizations.status`, `project_boundaries.active_boundary_tier`.
**When to use:** Every new Claim/Evidence/Conflict enum field in this phase (`claim.type`, `claim.status`, `evidence.source_type`, `evidence.validation_method`, `evidence.validation_status`, `conflict.type`, `conflict.severity`, `conflict.status`, `project.integrity_status`).

### Pattern 2: Idempotent migration guarded via pg_constraint
**What:** `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_constraint ...) ...$$` for constraints that don't support `IF NOT EXISTS` directly.
**When to use:** Every migration file in this phase — required because `npx supabase db reset` re-runs every migration from scratch and CI/local dev depends on idempotency.
**Example:**
```sql
-- Source: supabase/migrations/202608160001_scope_document_hash_uniqueness_by_type.sql:8-19
do $$
begin
  if not exists (
    select 1 from pg_constraint
    where conname = 'documents_project_type_sha256_key'
      and conrelid = 'documents'::regclass
  ) then
    alter table documents
      add constraint documents_project_type_sha256_key unique (project_id, document_type, sha256_hash);
  end if;
end $$;
```

### Pattern 3: RLS-enabled, backend-only operational tables (no select policy)
**What:** `enable row level security` + `revoke insert, update, delete from anon, authenticated` + **no** `create policy` for select. All reads/writes go through `backend_app` with its own auth/role guard.
**When to use:** `claims`, `evidence`, `conflicts`, `risk_assessments` — none of these should be directly queryable by Supabase client-side SDK; they are internal integrity data exposed selectively through vetted `/api/v1` endpoints (matches `project_boundaries`, `certification_pendencies`, `treasury_authorizations`).
**Example:**
```sql
-- Source: supabase/migrations/202608150003_project_boundaries.sql:54-58
alter table project_boundaries enable row level security;
revoke insert, update, delete on project_boundaries from anon, authenticated;
-- Sem policy de select: ver D-GEO-01 no cabecalho.
```

### Pattern 4: Recalculate-on-event, single commit per request (no async queue)
**What:** State (credit lock, treasury authorization, risk score) is recomputed synchronously inside the same request/transaction that changed the triggering data, then committed once.
**When to use:** `recalculate_risk_score` after any Claim/Evidence/Conflict write (D-14). Follow `CertifierService.record_decision`'s structure: validate → write dependent rows → single `await self.session.commit()` at the end.
**Example:**

### Anti-Patterns to Avoid
- **Recreating overlap detection SQL for Conflict:** `detect_boundary_overlaps` already has the correct GiST-indexed `ST_Intersects` pre-filter and `ST_Area(...::geography)` cast. Wrap/call it; do not write a second `ST_Intersects` query for Conflict — this would double the geometry computation cost and risk the two queries drifting out of sync.
- **Creating a new Claim on certification decision:** D-01 is explicit — certifier decisions produce Evidence/validation events over existing Claims, not new Claims. A new `CertifierService.record_decision` code path that calls `create_origination_claims` again would be a spec violation.
- **Blocking `projects.status` transitions from `integrity_status`:** D-05 explicitly scopes this phase to "informative + Auto Hold only." Do not add a guard in `CertifierService.record_decision` that raises `HTTPException` based on `integrity_status` — that's Phase 05.1 with Four-Eyes review.
- **New Postgres ENUM types via `CREATE TYPE`:** would break the established convention (see Standard Stack alternatives) and require future `ALTER TYPE ADD VALUE` migrations, which cannot run inside a transaction block in Postgres < 12 semantics and complicate `db reset` — the existing project has deliberately moved away from this since Phase 4.
- **Async/queued risk recalculation:** No Celery/Redis exists in this deploy (Dokploy single container — confirmed by Phase 05 CONTEXT.md's explicit rejection of Celery/Redis for the *scheduled* satellite job, a much better fit for async than this synchronous, per-request recalculation).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Geometry intersection / overlap percentage | A second `ST_Intersects` query, or worse, a Python/shapely equivalent | `ProjectsService.detect_boundary_overlaps` (service.py:1071), called from the new Conflict-persisting wrapper | Already GiST-indexed, already tested (`tests/test_project_boundaries.py`), already handles the `::geography` cast correctly for percentage math |
| Document hashing / dedup | New hash column or dedup logic on a new "Evidence documents" table | `documents.sha256_hash` + `documents_project_type_sha256_key` unique constraint (D-07) | Just fixed in `202608160001_scope_document_hash_uniqueness_by_type.sql`; recomputing hashing for Evidence would create two sources of truth for the same file |
| Audit trail of Claim/Evidence/Conflict/Risk changes | A new `integrity_events` table | `audit_events` + `create_audit_event()` helper (`backend_app/db/repositories.py:22`) | Existing table already supports `entity_type`/`entity_id`/`before_data`/`after_data`/`metadata`; a second audit mechanism would fragment the audit trail the certifier/boundary code already relies on |
| Risk signal weighting / explainability structure | Ad-hoc dict built inline in a route handler | A small `risk_engine.py` pure-function module (`compute_signals(claims, evidence, conflicts, weights) -> list[RiskSignalDTO]`) that is unit-testable without hitting the DB | D-15 requires the signal list to be recoverable via API, not just logged — a pure function is trivial to unit test and to expose through `GET /projects/{id}/integrity` |
| Configurable thresholds | A new dynamic-config table in Postgres | `backend_app/core/config.py` `Settings` fields, read via `get_settings()` (D-10/D-13 explicitly reject a dynamic-config table for this phase) | Matches every other configuration knob in the repo (`cors_origins`, `access_token_minutes`) |

**Key insight:** Nearly everything this phase needs (geometry math, hashing, audit trail, config pattern) already exists in a working, tested form one layer down (Phase 04.1/04/1/original schema). The actual net-new work is thin: three tables, four hook points, and one pure risk-scoring function.

## Common Pitfalls

### Pitfall 1: Double-computing overlap (Conflict vs. `GET /boundary-overlaps`)
**What goes wrong:** Building a separate query for Conflict persistence that doesn't match `detect_boundary_overlaps`'s output, so the existing `GET /projects/{id}/boundary-overlaps` endpoint (contract-frozen — used by existing tests) and the new persisted `Conflict.overlap_percentage` silently diverge over time.
**Why it happens:** Tempting to write `INSERT INTO conflicts SELECT ...` directly in SQL for performance, bypassing the Python method.
**How to avoid:** Have the new "detect and persist conflicts" method call `detect_boundary_overlaps(project_id)` internally and iterate its Python-side results to build `Conflict` rows. Same source of truth, same rounding.
**Warning signs:** A migration or service method containing `ST_Intersects` outside of `service.py:1071` and its new wrapper.

### Pitfall 2: Assuming `ProjectCreate.tags`/`ProjectCreate` carries an explicit ownership-vs-possession field
**What goes wrong:** D-01 says LAND_OWNERSHIP vs LAND_POSSESSION should be chosen "conforme o campo declarado pelo produtor" — but `ProjectCreate` (schemas.py:241-252) has no such field, and the frontend wizard's `documentTypeOptions` only offers `LEGAL_OWNERSHIP` or `CAR` as document types (`src/pages/Dashboard/AddProject.tsx:80-86`), not a structured ownership-type declaration.
**Why it happens:** The Bible spec (section 6, `Claim.type`) assumes a richer intake form than what Phase 3 actually built.
**How to avoid:** Either (a) default every origination Claim to `LAND_OWNERSHIP` when a `LEGAL_OWNERSHIP` document exists in the project's documents and fall back to `LAND_POSSESSION` otherwise (derived from Document, not from a new required field — matches D-07's "Document that feeds a Claim" framing), or (b) add a minimal new field to `ProjectCreate`/wizard. Do NOT silently invent a field name and assume it already exists in the payload.
**Warning signs:** Planner writes a task that reads `payload.ownership_type` or similar without first checking `ProjectCreate`.

### Pitfall 3: Evidence created before the Document it references is flushed
**What goes wrong:** `Evidence.document_id` needs a real `documents.id`; if Evidence creation runs before `await self.session.flush()` on the Document insert, the FK will be `None`/fail.
**Why it happens:** All three Document-creation call sites (`submit_project_draft:737`, `upload_project_document` routes.py:530, certifier `_persist_certificate:121`) call `session.add(document)` then `await session.flush()` shortly after — Evidence creation must be inserted *after* that flush, in the same pattern.
**How to avoid:** Insert the `create_evidence_for_document(document, ...)` call immediately after each existing `await session.flush()` that follows a `Document` insert.
**Warning signs:** IntegrityError on `evidence.document_id` FK during tests.

### Pitfall 4: Auto Hold overwriting `project.status` instead of `project.integrity_status`
**What goes wrong:** D-06 is explicit that Auto Hold sets `integrity_status = ON_HOLD` and never touches `projects.status` (the 16-state operational enum). A naive implementation reusing the existing `"SUSPENDED"` status string (already used by `CertifierService.record_decision` on `DECISION_REJECT`, service.py:314) would collide semantically with an unrelated operational status.
**Why it happens:** `projects.status` already has a `"SUSPENDED"` value that looks tempting to reuse for a different concept.
**How to avoid:** `integrity_status` must be its own new column on `Project` with its own value set (`DECLARED, IDENTITY_VERIFIED, EVIDENCE_PENDING, EVIDENCE_VERIFIED, UNDER_REVIEW, INDEPENDENTLY_VERIFIED, VERIFIED, ON_HOLD, SUSPENDED, REVOKED, REJECTED` — Bible section 7), fully independent of `ProjectStatusEnum`.
**Warning signs:** Any code path that writes `project.status = "ON_HOLD"` (not a valid `ProjectStatusEnum` value — would break the existing check/enum constraint) or that writes `project.status = "SUSPENDED"` from risk-engine code (would collide with certifier rejection semantics tracked by `previous_status`/audit events in `record_decision`).

### Pitfall 5: Recomputing risk score without idempotent read
**What goes wrong:** `recalculate_risk_score` must be safe to call multiple times per request (it's called after Claim creation AND after Conflict creation AND after Evidence creation, per D-14). If it appends signals cumulatively instead of recomputing from scratch, scores will inflate.
**Why it happens:** Natural instinct is to "add points" incrementally like a running total.
**How to avoid:** Each call should be a pure recompute: read current Claim/Evidence/Conflict state for the project, compute the full signal list fresh, and either (a) upsert a single current `RiskAssessment` row per project (like `project_boundaries`'s `on conflict (project_id) do update`) or (b) insert a new immutable `RiskAssessment` row per recompute (like `certifications`, append-only) and always read "latest by created_at" for the current score. Given D-15's audit/explainability requirement, prefer (b) — append-only — so risk history over time is inspectable, mirroring `Certification`.
**Warning signs:** `risk_score` monotonically increasing on every project edit even when nothing risk-relevant changed.

### Pitfall 6: `active_boundary` intersects itself in `detect_boundary_overlaps` after project update
**What goes wrong:** `persist_project_boundary` runs on both `create_project` and `update_project` (D-11: "roda de forma síncrona logo após criação/atualização de active_boundary"). Calling the Conflict-persisting wrapper from `update_project` too means old `Conflict` rows for that project need to be superseded, not just appended, or a project accumulates duplicate/stale conflicts every time its boundary is edited.
**Why it happens:** `create_project` and `update_project` are two separate methods (service.py:778 and 895); it's easy to wire the new Conflict logic into only one of them.
**How to avoid:** Extract a single `_sync_boundary_dependent_state(project)` helper called from both `create_project` (after `persist_project_boundary`) and `update_project` (after its own boundary persistence, if any), which re-derives Conflict rows for that project (e.g., mark previous `OPEN` conflicts as `status=RESOLVED` if no longer intersecting, upsert current ones) rather than blindly inserting.
**Warning signs:** `GET /projects/{id}/conflicts` returning duplicate rows for the same `relatedProjectId` after a boundary edit.

## Open Questions (RESOLVED — see 04.2-CONTEXT.md D-22, D-23)

1. **Exact `Evidence` → `Claim` linkage when a Document doesn't map cleanly to one of the two origination Claims**
   - What we know: D-07 says every Document that "alimenta um Claim" gets an auto-linked Evidence. Origination creates exactly two Claims (`LAND_OWNERSHIP`/`LAND_POSSESSION`, `RIGHT_TO_OPERATE`). Document types include `FOREST_INVENTORY`, `KML_OR_SHP`, `OTHER` which don't obviously map to either Claim.
   - What's unclear: Should `FOREST_INVENTORY`/`KML_OR_SHP`/`OTHER` documents get Evidence linked to `RIGHT_TO_OPERATE` (the more generic Claim), get no Evidence at all, or get Evidence with `claim_id = NULL`? The Bible's `Evidence.claimId` field (section 6) implies a required FK.
   - Recommendation: Default unmapped document types to link Evidence against the `RIGHT_TO_OPERATE` Claim (broadest applicability — a forest inventory or KML supports the operational claim more than a narrow ownership claim), and make `Evidence.claim_id` nullable in the schema as a safety valve, but treat "no Claim to link to" as a case the planner should explicitly decide, not silently allow.

2. **Whether `recalculate_risk_score` should also run on `update_project` (edits after origination, not just create)**
   - What we know: D-14 says risk recalculates "sempre que Claim, Evidence ou Conflict do projeto mudam." `update_project` (service.py:895) can change `payload.tags`, which cascades into `persist_project_boundary`, which can change overlap/Conflict state.
   - What's unclear: CONTEXT.md's code_context section only explicitly calls out the `create_project` hook point; `update_project`'s boundary-mutation path isn't mentioned by name.
   - Recommendation: Treat `update_project`'s boundary-touching path as in-scope for the Conflict-resync + risk-recalculation hook too (Pitfall #6), since Conflict/risk state legitimately changes when a geometry is edited — this is a natural reading of D-11/D-14, not a scope expansion.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Cross-org Conflict/risk data leakage (organization A learns organization B's project exists/overlaps via a guessable Conflict ID) | Information Disclosure | Reuse `_assert_project_edit_permission` org-scoping on every new internal Claim/Evidence/Conflict/risk route, exactly as done for `/projects/{id}/boundary-overlaps` and `/projects/{id}/pendencies` |
| Public dossier over-exposing internal risk signal detail (e.g., raw signal reasons revealing another party's document metadata) | Information Disclosure | Apply the same minimization principle as `PUBLIC_DOCUMENT_TYPES`/`public_document_item`: define an explicit allowlist of which risk signals/conflict fields are public-safe before extending `get_public_dossier`, do not simply serialize the internal `risk_signals` table verbatim |
| Risk score / Auto Hold tampering via direct writes | Tampering | New tables get RLS enabled + `revoke insert, update, delete from anon, authenticated`, no select policy — matches `project_boundaries`/`certification_pendencies` (D-GEO-01 precedent); all writes go through `backend_app` service methods, never client-side Supabase calls |
| Claim/Evidence spoofing (a producer submitting a Claim as VERIFIED directly via API) | Spoofing / Elevation of Privilege | D-01/D-03 already close this: every Claim is system-created from already-authenticated, already-validated Phase 3 fields (never a raw user-supplied `status` field); no route should accept a client-supplied `status`/`confidenceScore` for Claim creation |

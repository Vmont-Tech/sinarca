## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Supabase anon/authenticated client → Postgres | Frontend holds the Supabase anon key; any table without correct RLS is directly readable/writable, bypassing `backend_app` | Row-level access to `claims`/`evidence`/`conflicts`/`risk_assessments`/`risk_signals` |
| Migration → existing schema | A bad migration could alter `projects.status` semantics (16-state operational enum) and break certification/treasury | `projects` table DDL |
| Authenticated client → `POST /api/v1/projects` | Producer payload; must not influence Claim status/confidence | Project creation payload |
| Organization A → `GET /projects/{id}/claims,evidence,conflicts,integrity` | Claim/Evidence/Conflict/risk data of another org's project is internal | Cross-org read attempts |
| Multipart upload → `Evidence.hash` | The hash is the integrity anchor; if client-supplied it is worthless | Document upload bytes/hash |
| Risk Engine → `projects.status` | If the engine wrote to the wrong column it would corrupt certification/treasury flow | `project.integrity_status`/`risk_score` writes |
| Anonymous visitor → `GET /projects/{id}/public-dossier` | Unauthenticated endpoint; everything returned here is public forever | `integrity` block of the public dossier |

## Accepted Risks Log

| Risk ID | Threat Ref | Rationale | Accepted By | Date |
|---------|------------|-----------|-------------|------|
| AR-04.2-01 | T-04.2-18 | Synchronous risk recalculation fires on every Claim/Evidence/Conflict-affecting event (project create, boundary update, document upload, certifier decision). Each recalculation reads a few dozen rows per project and runs a pure in-memory function — no unbounded fan-out, no external calls. This matches the already-established "recalculate on event" pattern used by the certification workbench (D-14, locked decision) and is coherent with the current single-container deployment. Plan 04's threat register flags this explicitly for re-evaluation if `risk_assessments` grows beyond ~10^5 rows, at which point async/batched recalculation should be revisited. | gsd-security-auditor (04.2 retroactive audit) | 2026-08-16 |
| AR-04.2-02 | T-04.2-24 | `conflictCount` in the public dossier `integrity` block is a bare integer — no related-project id, friendly_id, name, or geometry is exposed alongside it. This is exactly the level of transparency the Bible (§40/§41, Overlap Check) requires for the public Trust vocabulary, and a count alone does not allow a visitor to identify or geolocate the neighboring project. `public_integrity_item()`'s allowlist (T-04.2-21) enforces that no richer field ever reaches this endpoint. | gsd-security-auditor (04.2 retroactive audit) | 2026-08-16 |

- `pytest tests/test_risk_engine.py -q` — 19/19 passed (pure, zero-DB-import module confirmed by grep)
- `pytest tests/test_project_conflicts.py -q` — 9/9 passed in isolation; 8/9 passed in one full-file batch run due to `test_double_claim_only_for_overlapping_pairs` hitting an incidental geometry collision with accumulated random-coordinate test data in the long-lived local dev Postgres (no DB reset between historical test runs in this environment). Re-ran the single test 3x in isolation — passed every time. This is a test-isolation/data-hygiene artifact of the shared local dev database, not a gap in the DOUBLE_CLAIM restriction itself: code review confirms `detect_and_persist_conflicts` only evaluates DOUBLE_CLAIM over pairs already returned by `detect_boundary_overlaps` (T-04.2-13's actual mitigation), so a real overlap did exist for the colliding pair — the assertion was simply too strong for a database that accumulates rows across unrelated historical runs. Not an OPEN_THREAT; noted for the team as a data-hygiene observation (consider `npx -y supabase db reset` before conflict-test runs, or tighter coordinate isolation).
- `pytest tests/contract/test_frontend_project_links.py -q` — 18/18 passed
- Migration greps: `create policy` = 0/0, `drop table`/`drop column` = 0/0, RLS `enable row level security` = 3 (core) + 2 (risk) = 5/5 tables

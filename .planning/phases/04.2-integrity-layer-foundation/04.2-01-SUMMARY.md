## Decisions Made

- `integrity_status`/`risk_score` are additive `projects` columns, fully parallel to `ProjectStatusEnum` — never written together with `status='ON_HOLD'` semantics (D-04, RESEARCH pitfall #4).
- No new Postgres `ENUM` type created anywhere; all new string-vocabulary columns use `text` + `check (col in (...))`, matching the repo's Phase 04 convention.
- No `select` RLS policy added on any of the 5 new tables — same sensitivity class as `project_boundaries` (conflicts reveal existence/proximity of third-party projects, evidence/claims carry PII-adjacent identity data). All reads go through `/api/v1` with org-scoped guards in later plans.

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Fixed stale `ON CONFLICT` target in `supabase/seed.sql` documents upsert**
- **Found during:** Task 3 (`npx -y supabase db reset`)
- **Issue:** A prior, unrelated commit (`39d0329 fix(documents): scope hash uniqueness by document_type`, migration `202608160001_scope_document_hash_uniqueness_by_type.sql`) dropped the old `documents_project_sha256_key` unique constraint `(project_id, sha256_hash)` and replaced it with `documents_project_type_sha256_key` `(project_id, document_type, sha256_hash)`. `supabase/seed.sql`'s `documents` insert was never updated to match, so seeding failed with `ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification (SQLSTATE 42P10)` — blocking `db reset`, which is mandatory for this task (per plan, false-positive verification without it).
- **Fix:** Updated the single `on conflict (project_id, sha256_hash)` clause in `supabase/seed.sql` to `on conflict (project_id, document_type, sha256_hash)`, matching the live constraint.
- **Files modified:** `supabase/seed.sql`

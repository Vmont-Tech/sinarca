### 2. Creating a project generates origination Claims (INTG-01)
expected: |
  A producer submits a new project via POST /api/v1/projects. Without any extra
  action, the project gets exactly 2 Claims (a land claim + right-to-operate), both
  status DECLARED with a low, server-computed confidence score — never a status the
  client could have supplied.
result: pass
evidence: |
  Logged in as `produtor@sinarca.com.br`, created a real project ("Projeto UAT
  Integrity", friendlyId PRC-2026-1105) via `POST /api/v1/projects` with a real 4-QTAG
  rectangle → `201`. `GET /api/v1/projects/PRC-2026-1105/claims` immediately after →
  `total: 2`, claims `LAND_POSSESSION` (statement: "Produtor declara posse da area de
  104.93 ha em Porto Nacional/TO.") and `RIGHT_TO_OPERATE`, both `status: "DECLARED"`,
  `confidenceScore: 10` — nothing in the creation payload could have set these.

### 3. Document upload creates Evidence with the real file hash (INTG-02)
expected: |
  Uploading a document to the project creates an Evidence row whose hash is exactly
  the uploaded file's sha256 (never recomputed elsewhere), linked to a Claim, with
  validationMethod limited to HASH_INTEGRITY or STRUCTURAL_COMPLETENESS.
result: pass
evidence: |
  Uploaded a real PDF as `LEGAL_OWNERSHIP` via `POST /api/v1/projects/PRC-2026-1105
  /documents` → `201`, `sha256: 3e19daf7...9267e`. `GET /api/v1/projects/PRC-2026-1105
  /evidence` → an Evidence row with `hash: "3e19daf7...9267e"` (byte-identical to the
  upload response), `validationMethod: "HASH_INTEGRITY"`, `validationStatus:
  "VERIFIED"`, `sourceType: "SELF_DECLARED"`, `claimId` populated (not null). A second
  Evidence row for dossier structural completeness also present with
  `validationMethod: "STRUCTURAL_COMPLETENESS"`.

### 5. Overlapping geometry generates a Conflict with severity (INTG-03)
expected: |
  When a new project's boundary overlaps existing projects above the configured
  threshold, Conflict rows are created automatically with a severity class
  (CLEAR→CRITICAL) — no manual trigger required.
result: pass
evidence: |
  `GET /api/v1/projects/PRC-2026-1105/integrity` right after creation shows
  `conflictCount: 1086` and risk signals including `OVERLAP_CRITICAL` ("+50 541
  sobreposições geoespaciais acima de 50% da área do projeto"), `OVERLAP_MEDIUM`,
  `OVERLAP_LOW`, and `DOUBLE_CLAIM` ("+60 Mesmo atributo ambiental reivindicado na área
  sobreposta por 543 outros projetos") — all computed automatically from the shared
  test-fixture rectangle without any explicit "detect conflicts" call from this
  session. Severity classes present exactly as designed (CRITICAL/MEDIUM/LOW), not a
  flat number.

### 6. Risk Score is computed with explainable signals and triggers Auto Hold on CRITICAL (INTG-04)
expected: |
  The project's risk score (0-100) is computed from real Claim/Evidence/Conflict
  state, every point is attached to a human-readable reason, and a CRITICAL score
  automatically sets integrity_status to ON_HOLD — without touching the operational
  projects.status.
result: pass
evidence: |
  Same live project: `riskScore: 100`, `riskClass: "CRITICAL"`, `autoHold: true`,
  `integrityStatus: "ON_HOLD"`, each of the 7 signals carries an explicit
  `"+N <plain PT-BR reason>"` string (e.g. "+20 Declaração de posse da terra sem
  evidência validada"), never a bare number. Cross-checked
  `GET /api/v1/projects/PRC-2026-1105/public-dossier` in the same moment:
  `project.status = "AWAITING_CERTIFICATION"` (the operational workflow status,
  completely unaffected) while `project.integrity.publicStatus = "ON_HOLD"` — proves
  D-04/D-05/D-06 hold live, not just in unit tests.

### 7. Public status vocabulary never shows a bare "Certified" (INTG-05)
expected: |
  The public dossier's integrity block uses the D-16 vocabulary (Declared/Verified/
  Under Review/On Hold/Suspended/Revoked) and only exposes a minimized, public-safe
  set of fields — never the internal integrity_status, autoHold flag, or raw
  claim/conflict identifiers of other organizations.
result: pass
evidence: |
  `GET /api/v1/projects/PRC-2026-1105/public-dossier`'s `integrity` block contains
  exactly: `publicStatus, riskScore, riskClass, conflictCount, assessedAt, signals`
  (each signal: `code, weight, reason` only) — no `integrityStatus`, `autoHold`,
  `trigger`, or `claimCount` (all present in the internal `/integrity` endpoint from
  Test 6, correctly absent here). `publicStatus: "ON_HOLD"` uses the D-16 vocabulary,
  not "Certified". Frontend copy for this vocabulary
  (`src/pages/Dashboard/MrcaDetails.tsx`) was read and reviewed directly during the
  Plan 04.2-05 human-verify checkpoint: the integrity pill always renders alongside
  the operational status pill (`statusLabel(project.status)` + `Integridade:
  {integrityStatusLabel(...)}` on the same line), never alone, and the explanatory
  paragraph explicitly states integrity status "não substitui auditoria independente,
  ainda não disponível nesta fase" — no overclaiming. `npm run build` succeeded
  (verified during Plan 04.2-05 execution) and
  `pytest tests/contract/test_frontend_project_links.py -x -q` — 18 passed.

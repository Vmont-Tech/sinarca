# Phase 04.2 Plan 04: Risk Engine (Score, Signals, Auto Hold) Summary

**Pure `risk_engine.py` (signals -> score -> class -> integrity_status) feeding an append-only `IntegrityService.recalculate_risk_score` that fires synchronously at 5 lifecycle events, non-discretionarily locks `CRITICAL` projects into `integrity_status=ON_HOLD` without ever touching `projects.status`, and exposes the full explanation via `GET /projects/{id}/integrity`.**

## Accomplishments

- `backend_app/modules/integrity/risk_engine.py`: zero-DB-import pure module. `compute_signals` maps `ClaimSnapshot`/`ConflictSnapshot` dataclasses to at most one `RiskSignalDTO` per bucket (OVERLAP_CRITICAL/HIGH/MEDIUM/LOW, DOUBLE_CLAIM, LAND_CLAIM_UNVERIFIED, CLAIM_EVIDENCE_PENDING, POSSESSION_WITHOUT_TITLE), with counts folded into `reason`/`metadata` instead of multiplying weight (no accumulative inflation across repeat conflicts). `score_from_signals` saturates at 100. `risk_class_for_score` maps to `RISK_CLASS_BOUNDS`. `integrity_status_for` implements the D-06 non-discretionary gate (`CRITICAL` -> `ON_HOLD`; never assigns `VERIFIED`/`IDENTITY_VERIFIED`/`INDEPENDENTLY_VERIFIED` in this phase).
- `tests/test_risk_engine.py`: 19 unit tests with zero DB/HTTP/event-loop dependencies, covering every `<behavior>` item plus the D-13 (configurable weights via `Settings`) and T-04.2-16 (no third-party project identifiers in `reason`) requirements.
- `IntegrityService.recalculate_risk_score`: re-reads all `Claim`/`Evidence`/`Conflict` rows for the project on every call (no accumulated state -> idempotent), appends one `ProjectRiskAssessment` + N `RiskSignal` rows (append-only, D-19), writes only `project.integrity_status`/`project.risk_score` (grep-verified: zero `project.status` writes), and emits `RISK_RECALCULATED` plus a dedicated `INTEGRITY_AUTO_HOLD` audit event exactly on the transition into `CRITICAL` (D-06 non-discretionary trail).
- `IntegrityService.integrity_summary` / `recalculate_for_related` helpers and `GET /api/v1/projects/{id}/integrity` (org-scoped, same guard as `/claims`/`/evidence`/`/conflicts`).
- Risk recalculated synchronously at all 5 trigger points: `create_project` (PROJECT_CREATED + RELATED_CONFLICT_CHANGED for affected neighbors), `update_project`'s tags branch (BOUNDARY_UPDATED + RELATED_CONFLICT_CHANGED), `create_evidence_for_document` (EVIDENCE_CREATED), and `certifier.record_decision` (CERTIFICATION_DECISION, no blocking guard per D-05).
- 7 new contract tests plus fixes to keep them deterministic against a shared local Postgres.

## Triggers used

`PROJECT_CREATED`, `RELATED_CONFLICT_CHANGED`, `BOUNDARY_UPDATED`, `EVIDENCE_CREATED`, `CERTIFICATION_DECISION` — all 5 wired synchronously, all visible in the `trigger` field of `GET /projects/{id}/integrity`.

## Decisions Made

- `ProjectRiskAssessment.created_at` is now set explicitly from the application clock instead of the DB `server_default=func.now()`. Postgres' `now()` returns the transaction-start timestamp, identical for every statement in the same transaction — this made "the latest assessment" non-deterministic whenever two recalculations landed in the same commit (concretely: the `EVIDENCE_CREATED` hook firing while `_persist_certificate` attaches the certificate document, immediately followed by the `CERTIFICATION_DECISION` hook, both inside `record_decision`'s single commit). Caught live by `test_certifier_decision_recalculates_risk` failing with `trigger == 'EVIDENCE_CREATED'` instead of `'CERTIFICATION_DECISION'`; fixed by passing `created_at=datetime.now(timezone.utc)` explicitly on insert (Rule 1 — correctness bug directly caused by this task's own new code, not pre-existing).
- The plan's acceptance criterion `pytest ... -k "integrity or risk" -x -q coleta 7 testes` actually collects 8, because the pre-existing Plan 02 test `test_integrity_claims_endpoint_is_org_scoped` also matches the `integrity` keyword. All 8 pass; this is a harmless keyword-filter overlap, not a scope change — documented rather than silently renaming an already-shipped, already-passing test from a prior plan.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `ProjectRiskAssessment.created_at` non-deterministic ordering within a single transaction**
- **Found during:** Task 3, writing `test_certifier_decision_recalculates_risk`
- **Issue:** Two `recalculate_risk_score` calls inside the same DB transaction (certificate-attachment `EVIDENCE_CREATED` hook, then the new `CERTIFICATION_DECISION` hook in `record_decision`) produced identical `created_at` values because Postgres `now()`/`server_default` is transaction-time, not statement-time. `integrity_summary`'s `ORDER BY created_at DESC LIMIT 1` then returned an arbitrary row instead of the actually-latest one.
- **Fix:** `recalculate_risk_score` now passes `created_at=datetime.now(timezone.utc)` explicitly on `ProjectRiskAssessment` construction, using the Python-side wall clock which advances per call even within one DB transaction.
- **Files modified:** `backend_app/modules/integrity/service.py`
- **Verification:** `test_certifier_decision_recalculates_risk` passes deterministically; full suite green.
- **Committed in:** `5fdf1b3` (Task 3 commit)

## Issues Encountered

- First draft of `test_risk_recalculation_is_idempotent` compared the risk score *before* any geometry PATCH against the score *after two* PATCHes to a brand-new random rectangle — the score legitimately changed because the new location could overlap other test-session projects, which is not what idempotency means. Fixed by comparing the score after the *first* PATCH against the score after the *second, identical* PATCH (both to the same new tags), which is what the plan's spec actually describes. Self-caught during verification, test-only fix, no production code change.
- Two new test names (`test_identical_geometry_triggers_risk_auto_hold`, `test_risk_auto_hold_never_changes_operational_status`) were chosen to include "risk" specifically so they'd be picked up by the plan's own `-k "integrity or risk"` verification filter — an early draft used names without "risk"/"integrity" and was invisible to that filter.
